# 产品原则：复杂度迁移与渐进暴露

## 核心命题

产品设计的目标不在于替用户取消思考。目标是减少用户为了理解产品、记忆操作、寻找入口而付出的无价值认知成本，把注意力还给真正的任务：判断目标、选择方案、审阅内容和承担结果。

> 优秀的产品不消灭复杂性；它管理复杂性的暴露顺序。

## 分层复杂度

XHS-Chimera 采用“简单主路径 + 深层专业能力”的分层结构：

```text
默认路径
  → 高级设置 / 自定义
    → 工作流 / 自动化 / API / 专业能力
```

- **默认路径**：让首次使用者用最少步骤完成一个明确任务。
- **高级设置**：在用户需要改变默认行为时，提供清晰、局部的配置。
- **工作流与自动化**：面向熟练用户和团队，将重复步骤、规则、数据源与外部系统编排起来。

简单发生在路径上，不发生在能力阉割上。复杂能力可以暂时不出现，但必须可发现、可解释、可进入。

## 界面放置规则

功能的可见层级由三个因素共同决定：

```math
位置 \approx f(使用频率, 任务关键度, 理解成本)
```

| 情况 | 产品处理 |
|---|---|
| 高频 + 低理解成本 | 放在任务主界面，直接可用。 |
| 低频 + 高理解成本 | 放入高级设置、展开面板或专业工具区。 |
| 高频 + 高理解成本 | 重新设计成向导、推荐、预设、分步确认或渐进输入；不能把原始复杂度直接堆给用户。 |
| 低频 + 低理解成本 | 放在次级菜单或上下文动作中。 |

## 按时机暴露

复杂度不应固定地堆在某个“高级设置”页，而要根据任务阶段、熟练度与当前意图出现：

```math
复杂度 = f(任务阶段, 熟练度, 当前需求)
```

- 用户在建立账号时，只看到定位、目标和已有素材；需要品牌规范时再展开视觉系统。
- 用户在选择选题时，默认看到推荐方向与依据；需要时再查看数据源、评论证据、筛选条件和评分规则。
- 用户在编辑内容时，先看到可完成的内容包；需要时再进入分页、视觉、引用、版本差异和跨平台派生。
- 用户准备发布时，默认看到账号、预览、风险和确认；需要时再配置排期、幂等策略、任务日志和执行适配器。
- 用户成熟后，可收藏工作流、设置默认值、批量处理或通过 MCP/API 调用。

## 系统替用户承担什么

系统应承担产品复杂性和重复性：

- 保存账号、素材、草稿、选题与发布结果之间的关联；
- 在合适阶段提示缺失信息、风险和下一步；
- 给出基于用户上下文的默认值、推荐和可逆的预设；
- 将高级能力组织成可发现的“为什么需要它”和“何时使用它”；
- 把重复、机械、可验证的操作转成后台流程。

系统不应替用户承担价值判断：

- 账号真正要服务谁；
- 哪个选题符合用户的经验、品牌与长期目标；
- 内容是否真实、合适、可发布；
- 是否对外发布、何时发布、发布到哪个账号；
- 是否把某种用户需求发展为产品或服务。

## 对 XHS-Chimera 的直接约束

1. 首页不展示 Cookie、RPA、MCP、模型 Provider、任务锁等基础设施；这些只在产生对应需求时进入设置或专业区。
2. 用户主路径围绕“今天要完成什么内容任务”，而非“系统有哪些模块”。
3. 每一项高级功能都必须有：触发时机、默认值、可见入口、说明文本和退出/恢复路径。
4. AI 推荐必须显示简洁的理由与证据入口；用户可以接受、修改或忽略。
5. 自动化默认只准备和建议；涉及账号写入、批量分发或不可逆动作时，保留清楚的人工确认。
6. 熟练用户可以把重复任务保存为工作流，并从默认路径直接跳转到专业模式。

## 衡量标准

每次增加功能时先回答：

1. 用户在哪个任务阶段第一次需要它？
2. 默认情况下系统能否替用户准备好合理值？
3. 用户是否能在不理解该功能的情况下完成主任务？
4. 当用户需要它时，能否发现它、理解它、撤销它？
5. 这个功能减少的是产品操作负担，还是不恰当地替用户做了业务判断？
