# XHS-Chimera 产品架构与功能交付排序

## 1. 排序标准

功能优先级不按“代码好不好写”或“哪个案例最酷”决定，按以下四个因素判断：

```text
优先级 = 用户主路径贡献 × 问题痛度 × 后续功能依赖度 ÷ 实现与维护成本
```

- **用户主路径贡献**：是否让用户更快完成“发现机会→做成内容→获得反馈”。
- **问题痛度**：是否解决创作者高频、真实、阻塞性问题。
- **后续功能依赖度**：是否是其他功能的共同基础。
- **实现与维护成本**：数据源稳定性、许可证、浏览器依赖、模型成本、UI复杂度和长期维护负担。

### 不以此作为优先级

- 自动化程度；
- GitHub Star 数；
- 技术栈新旧；
- 能否宣传“全自动”；
- 是否已有现成爬虫或逆向接口。

## 2. 产品架构：以用户对象为中心

```text
┌───────────────────────────────────────────────────────────────────┐
│                         用户体验层                                  │
│ 今日工作台 / 账号画布 / 需求雷达 / 内容包 / 视觉工坊 / 复盘          │
└───────────────────────────────────────────────────────────────────┘
                                │
┌───────────────────────────────────────────────────────────────────┐
│                         内容经营领域层                              │
│ AccountProfile · ContentPillar · Evidence · Opportunity            │
│ ContentPackage · ContentVersion · CardPlan · PreflightReview       │
│ PublishPackage · PublishedContent · FeedbackSignal · LearningRecord│
└───────────────────────────────────────────────────────────────────┘
                                │
┌───────────────────────────────┼───────────────────────────────────┐
│ 研究适配器                    │ 创作/媒体适配器                   │
│ 手动录入                      │ LLM Provider                      │
│ URL/评论导入                  │ HTML/CSS Card Renderer             │
│ 浏览器/平台读取（后期）        │ Image Provider（后期）              │
├───────────────────────────────┼───────────────────────────────────┤
│ 发布适配器                    │ 数据适配器                         │
│ Preflight Gate                │ 手动数据/评论导入                  │
│ Safe Publish Orchestrator     │ 创作者后台同步（后期）              │
│ Playwright XHS Adapter        │                                    │
└───────────────────────────────┴───────────────────────────────────┘
                                │
┌───────────────────────────────────────────────────────────────────┐
│ 基础设施层：Tauri / TypeScript API / SQLite / 文件资产 / 队列 / 审计 │
│ MCP / Workflow / 多账号能力仅经领域层进入，不直连页面或浏览器        │
└───────────────────────────────────────────────────────────────────┘
```

### 架构规则

1. 页面不直接操作浏览器、数据库或模型；页面只调用领域服务。
2. 领域服务不依赖某个具体 LLM、浏览器、数据源或渲染器；通过 adapter 接口调用。
3. 所有内容都以 `ContentPackage → ContentVersion` 为中心，不能让文案、图片、发布任务彼此失联。
4. 所有外部证据都必须有来源、采集时间和原始片段。
5. 所有对账号的写操作都必须经过 `PreflightReview → PublishPackage → SafePublishOrchestrator`。
6. 高级能力只能扩展默认路径，不能另建一套脱离内容资产的平行系统。

## 3. 功能分层和交付排序

## P0：已落地 / 继续维护的发布安全基础

### 包含

- 明确人工确认；
- API、队列执行器双重确认；
- 发布前审基础；
- 账号级互斥；
- SQLite 持久化幂等；
- `confirmed` / `submitted_unconfirmed` / `captcha_blocked` / `failed` / `blocked` 状态语义；
- 未知状态、验证码和人工审查状态不自动重试；
- 已确认回执写入草稿和统计闭环。

### 用户价值

用户不会因产品黑箱、重复点击、任务冲突或未知回执而发错、重复发或盲目重发。

### 后续约束

P0 不再无限扩张。除修复和接入新发布包外，不继续优先做发布自动化功能。

---

## P1：内容经营最小闭环（最高优先级）

这是第一批应该真正开发的产品能力。完成后，即使不接自动抓取、自动生图或真实发布，用户也可以完成一次有价值的内容经营循环。

### P1.1 账号经营档案

**优先级：1 / 工作量：中 / 依赖：现有 accounts、drafts。**

#### 用户价值

用户不用反复向 AI 解释账号是谁、面对谁、讲什么；每一次内容生成都基于可编辑的长期上下文。

#### 核心实体

- `account_profiles`
- `content_pillars`
- `voice_samples`
- `brand_kits`（先只存视觉偏好和示例，不做完整设计器）

#### 最小功能

- 六步账号向导：目标、受众、可讲内容、栏目、边界、样本；
- 账号经营画布；
- 当前账号切换；
- 将档案摘要注入内容机会和内容包。

#### 后置能力

- 自动从历史内容提炼口吻；
- 视觉主体锁定；
- 团队共享档案与审批。

### P1.2 手动证据录入 + 内容机会卡

**优先级：2 / 工作量：中 / 依赖：账号经营档案。**

#### 用户价值

用户无需等待爬虫或复杂热点系统，就能把自己看到的评论、链接、聊天记录和用户问题转成有依据的选题。

#### 核心实体

- `research_evidence`
- `content_opportunities`
- `opportunity_evidence`
- `opportunity_decisions`

#### 最小功能

- 粘贴评论、笔记摘录、客户问题或 URL；
- 标记来源、采集时间、用户类型、问题类型；
- 从 1–20 条证据创建机会卡；
- 机会卡字段：受众、场景、问题、独特角度、目标、风险；
- 选题池：继续、推迟、拒绝、转为内容包。

#### 为什么先手动而非爬虫

用户价值是“把证据变成决策”；自动采集只是证据输入方式之一。先让闭环成立，再接浏览器/API adapter。

### P1.3 内容包 + 版本化编辑器

**优先级：3 / 工作量：大 / 依赖：账号档案、内容机会。**

#### 用户价值

用户得到可持续编辑、可追溯、可衔接视觉和发布的内容成品，而不是一次性 AI 文案。

#### 核心实体

- `content_packages`
- `content_versions`
- `content_sections`
- `platform_derivatives`（P1 只预留模型）

#### 最小功能

- 内容意图头部：写给谁、解决什么、为什么由我来讲；
- 标题、正文、标签的可编辑稿；
- 版本保存和版本差异；
- 证据/事实占位标记；
- 从机会卡生成内容结构；
- “改写一段”而不是覆盖全文；
- 将一个版本冻结为发布候选。

### P1.4 简易图文分页与发布包连接

**优先级：4 / 工作量：中 / 依赖：内容包。**

#### 用户价值

用户能看到文本如何变成可发布图文，不再在文案工具和排版工具之间搬运。

#### 最小功能

- 根据标题/正文生成可编辑分页建议；
- HTML/CSS 3:4 卡片渲染；
- 封面短标题；
- 用户上传图片和单页文本编辑；
- 生成媒体清单并连接既有发布前审与发布任务。

#### 不在 P1 做

- 自由画布；
- 高成本生图；
- 完整品牌模板市场；
- 跨平台视频渲染。

### P1 验收标准

用户可以：

```text
创建账号档案
→ 粘贴 3 条用户评论
→ 生成/编辑一个内容机会卡
→ 创建内容包并保存两个版本
→ 自动分页为图文卡片
→ 看到发布前审与账号确认
→ 选择保存或受控提交发布
```

## P2：让闭环更聪明、更省力

### P2.1 需求雷达自动输入

**优先级：5 / 工作量：大 / 依赖：P1 evidence/opportunity。**

- URL 导入、浏览器读取、评论/笔记批量导入；
- Evidence Normalizer；
- 问题、愿望、异议、咨询信号提取；
- 按账号匹配度、证据强度、栏目空白排序；
- 初级模式只显示少量机会，高级模式显示筛选器与原始证据。

**复用方向**：Lingzao 的研究工作流、CreatorHub 的观察模型、Business Validator 的机会报告结构。许可证不明确的项目只借鉴行为和数据模型，重写实现。

### P2.2 今日工作台

**优先级：6 / 工作量：中 / 依赖：P1/P2 数据。**

- 汇总“待做内容、待确认发布、待处理评论、新机会、栏目空白”；
- 只给少量解释性建议；
- 可从“为什么推荐”进入高级依据。

### P2.3 品牌视觉资产 + 样图确认

**优先级：7 / 工作量：中到大 / 依赖：内容包、卡片分页。**

- 品牌色、字体、封面规则、已批准样本；
- 先样图、后批量；
- 重做单页、替换素材、导出；
- 后接生图 provider。

**复用方向**：Visual Director 的页面计划和样图确认；Poster Studio 的设计器组织。MIT 可复用的代码仍需逐文件审查，优先提炼小模块。

### P2.4 手动复盘 + 反馈信号

**优先级：8 / 工作量：中 / 依赖：已发布内容、机会卡。**

- 手动导入点赞、收藏、评论、咨询数据；
- 评论标记问题/异议/需求；
- 一键从评论生成下一篇内容机会；
- 内容、栏目、账号三层的学习记录。

## P3：熟练用户和团队扩展

### P3.1 自动数据同步与评论研究

**优先级：9 / 工作量：大，维护成本高。**

- 创作者后台读取、评论同步、周期指标；
- 需要 adapter、失败恢复、登录状态和数据来源审计；
- 只作为 P2 手动复盘的自动输入，不改变复盘产品对象。

### P3.2 内容日历、系列与多账号协作

**优先级：10 / 工作量：大。**

- 系列内容地图；
- 多账号栏目覆盖；
- 审核人/发布人角色；
- 内容日历、排期、交接与审计；
- 账号矩阵和批量分发只在内容已审核后进入。

### P3.3 工作流、MCP/API、跨平台派生

**优先级：11 / 工作量：大。**

- 用户将重复流程保存为工作流；
- MCP/API 读取内容对象并提出建议；
- 所有账号写入仍走 P0 发布门；
- 内容包可派生公众号、视频脚本、其他平台文案。

### P3.4 高级视觉与视频工坊

**优先级：12 / 工作量：很大。**

- 完整自由画布；
- 生图/视频 provider；
- 口播、字幕、剪辑、跨平台视频分发；
- 不应阻塞 P1 的图文主路径。

## 4. 模块依赖图

```text
P0 发布安全底座
      ↑
账号经营档案 ────┐
      ↓           │
手动证据录入 → 内容机会卡 → 内容包与版本 → 图文分页 → 发布包 / P0
                                      ↓                    ↓
                                 品牌视觉资产          发布内容
                                      ↓                    ↓
需求雷达自动输入 ─────────────────────────────────→ 反馈信号 / 复盘
                                                             ↓
                                                       下一篇机会卡

熟练用户层：日历 / 团队 / 工作流 / MCP / 跨平台
只读取或扩展上述对象，不能绕过它们。
```

## 5. 推荐的代码边界

```text
api/
├─ domains/
│  ├─ accounts/        AccountProfile, ContentPillar, VoiceSample, BrandKit
│  ├─ research/        Evidence, Signal, Opportunity
│  ├─ content/         ContentPackage, Version, Section, Derivative
│  ├─ media/           CardPlan, CardPage, VisualAsset, RenderJob
│  ├─ review/          PreflightReview, RuleSet
│  ├─ publishing/      PublishPackage, PublishAttempt, existing safe guard
│  └─ insights/        MetricSnapshot, FeedbackSignal, LearningRecord
├─ adapters/
│  ├─ evidence/        Manual, URL, Browser, API
│  ├─ ai/              LLM providers
│  ├─ renderer/        HTML/CSS, image provider
│  ├─ publisher/       XHS Playwright, optional OpenClaw, future platforms
│  └─ analytics/       Manual import, creator dashboard
├─ orchestration/
│  ├─ today-brief/
│  ├─ content-workflow/
│  └─ safe-publish/
└─ routes/
```

现有 `api/services/` 可以逐步迁移，不要求一次重构。新功能从 `domains/` 开始，旧模块通过 adapter 兼容。

## 6. 本轮建议的下一项实现

**直接开始 P1.1：账号经营档案。**

原因：它是需求雷达、内容机会、内容包、视觉和复盘共同需要的上下文根；用户能直接看见价值；实现成本可控；无需依赖不稳定抓取或真实平台写入。

第一条垂直切片：

```text
选择账号
→ 填写账号目标、目标用户、可讲内容、栏目、边界
→ 保存
→ 在草稿/内容创建页显示“本次内容将基于此账号档案”
```

完成后再做 P1.2 手动证据录入和内容机会卡。
